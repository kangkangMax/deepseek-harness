Ideation

Composer Worktree 开关

  • Date 2026-10-10
  • Topic composer-worktree-toggle
  • Mode repo-grounded
  • Focus 对话框内的 Worktree 开关 + 首个 prompt 触发自动创建 + 用新目录开始会话

在 dsh 的 composer 里加一个 Worktree 开关：勾选后用户输入 prompt，系统自动创建 worktree 与目录，并让会话在该目录里开始——对标 Claude Code 的同类能力。

Grounding Context

dsh 是 pnpm monorepo + TypeScript 的 cordis 插件架构，客户端是 React + 自研 slot 系统。composer 已经有一族「模式开关 / 选择器」：conversation.input.plan、conversation.input.model、conversation.input.permission；完整的开关先例是 packages/client/ui-plan（客户端半边）+ packages/plan/plan-mode（宿主半边）。

宿主侧可用的触发点是 session/created、agent/created、agent/pre-step、agent/request、agent/turn-stopping——没有单一的 turn/start。会话的 header.cwd 在创建时一次性写入并冻结，收养一个 cwd 不同的会话会抛 ApiSessionCwdConflict；workspace-write 的写围栏根取自同一个 header.cwd。

官方实验性 worktree（仅 0.2.1-alpha.2 线）：服务 ctx.worktrees 只暴露 create(agent, {name?, from?})，默认落点 <仓库根>/.agents/worktrees/<name>，并自述「不拥有工作树注册表、清理计划、分支合并策略或任务关联数据库」。第三方 dsh-git-worktree 已经提供了 /worktree 命令族、一套 managed-checkouts 注册表，并替换了官方的 workspace UI 提供方；它让 worktree 会话仍然归属同一个 workspace（靠 projectId），只把会话的 cwd 换掉。

外部先例：Claude Code 的 CLI 用 -w/--worktree 在启动时创建（.claude/worktrees/<slug>、分支 worktree-<slug>、用 git worktree add -B 复位孤儿分支），桌面端则每个新会话自动建，且后台会话先在工作目录、首次编辑前才移入；Cursor 3 的 Agents Window 支持最多 10 路并行与 /best-of-n，但其 Windows 用户实测 2GB 仓库 20 分钟生成 9.82GB worktree、一周累积约 140GB；gwq 用层级命名且刻意不维护注册表；Neon branch 用 COW + expires_at TTL 做「廉价创建 + 到期回收」。

1

会话出生地决议：开关是一次性上膛，不是会话内模式

Description
勾选不在当前会话里翻转一个状态，而是登记一个「下一次会话的出生地」意图。用户按下发送时，宿主原子兑现两件事：先物化 worktree，再以该目录为 cwd 创建会话。会话一旦存在就已经在 worktree 里，不存在「切换 cwd」这一步。勾选态在兑现后自动归位，隔离态的持续表达交给常驻徽章（见方向 5）。
Axis
1 触发时机与状态机
Basis
direct会话创建路径在 packages/api/session-controller/src/agent.ts 里就把 cwd 绑定进会话身份，且已有会话 cwd 不一致即抛 ApiSessionCwdConflict；packages/core/session/src/index.ts 的 header 一次性构造并冻结，cwd 仅由创建元数据写入。externalClaude Code 桌面端「每个新会话自动建 worktree」。
Rationale
整个切片里唯一不可逆的一步就是会话 cwd，而它恰好只能在「会话尚不存在」的这一刻设定。把这个顺序钉死，后面所有「每 prompt 一副本」「fork 自带副本」的能力都退化成它的调用方；顺序错了，任何「先开会话再迁移」的路线都会撞 ApiSessionCwdConflict。
Downsides
勾选态是瞬时的，不熟悉的人会找不到「取消勾选」；已有会话无法原地进入 worktree，只能新建——需要在 UI 文案上明说。
Confidence 88%Complexity Medium
2

不新增第四种落点：开关只向已装配的 provider 下单

Description
开关自己不调 git、不定落点、不维护第二套状态。它向「当前装配的 worktree provider」发一个创建请求——官方 ctx.worktrees.create 或第三方插件都能接；命名由 provider 的确定性规则派生（同一 prompt + 同一会话重试落回同一路径），落点与保留策略都跟着 provider 走。
Axis
2 落点与命名
Basis
direct~/.dsh/plugins/dsh-git-worktree/managed-checkouts.json 已是一套真实的会话↔检出绑定实体（含 phase 与 delivery）；第三方 lib/workspace-provider-lifecycle.js 里 ctx.provide('worktreeWorkspaceProvider', true) 逐字对上，证明「worktree 能力提供方」在装配层是可替换的一等概念。
Rationale
机器上已经有三套落点约定。若开关自建，就出现第四种，正好加重它想解决的混乱；让 provider 决定落点，开关是唯一入口且不新增约定。同一份状态也避免「谁的 list 更准」这类双写者漂移。
Downsides
把落点与命名的最终解释权交给 provider，意味着开关的行为随装配变化；没有 provider 时必须有明确降级（拒绝勾选并说明），而不是静默走一条内建默认路径。
Confidence 82%Complexity Medium
3

会话记录持有来源与生命周期

Description
创建时往会话日志写一条 log-only 的事件（落点、分支、基点 commit、创建者）。「来源 / 是否脏 / 是否有未合并 commit / 是否到期」全部由投影从日志折叠出来，不另建注册表。回收由同一条投影驱动：无改动且无未合并 → 到期回收；有改动 → 转保留并提示。
Axis
3 回收与生命周期
Basis
directplan-mode 已用「log-only 事件 + projection 折叠」保存跨重启状态，并明示 resume 与 fork 都会还原；alpha.2 的决策笔记原文：「该服务不拥有工作树注册表、清理计划、分支合并策略或任务关联数据库」。externalNeon branch 的 expires_at TTL（1h–30d）。
Rationale
既然创建由我们发起，来源就不必再靠路径前缀猜测——它是记录，不是推断。这同时消掉「来源误标」这一整类风险，并把「谁负责删」从悬空问题变成「会话归档即触发回收」的确定规则。
Downsides
投影只覆盖由开关创建的 worktree；机器上既有的历史残留仍只能靠路径推断。两套来源判定并存需要在 UI 上区分「已知」与「推断」。
Confidence 80%Complexity Medium
4

围栏原子切换并回显

Description
沙箱的写围栏根取自 session.header.cwd，右侧栏文件树根也是。因此「建树 + 新会话 + cwd + 围栏根」必须是同一次原子动作，且 composer 要显式回显「当前围栏根是哪个目录」。否则会出现最难查的一类故障：开关看起来生效了，agent 却写不进 worktree（或反过来，被锁在主仓之外）。
Axis
4 会话与上下文迁移
Basis
directpackages/sandbox/sandbox-policy/src/index.ts 里 workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? …)——围栏根与会话 cwd 同源。（此前本档把这条依据记成了某第三方 README 的本地路径，该路径不存在；已按仓库内证据更正。）
Rationale
这是「开关开了但功能不动」的典型成因，用户不会想到是沙箱围栏，只会以为 worktree 坏了。把围栏切换列为开关必须一并修改并回显的状态，可以消掉这一类静默失败。
Downsides
把围栏根做成可见状态，意味着 composer 上要多一处常驻信息，与「只在不可逆动作时打扰用户」的取向（方向 5）需要划清边界。
Confidence 85%Complexity Low
5

隔离态常驻可见，只在不可逆动作时强制显形

Description
composer 上一个安静的常驻徽章读同一份投影：分支、落点、未提交数、未合并数。创建过程不弹确认、不铺横幅；只有当用户要做不可逆动作（合并、丢弃、删除）时，才出现一次不可省略的提示。可见性的注意力预算从「入口确认」搬到「出口决策」。
Axis
5 可见性与可控性
Basis
directpackages/client/ui-plan 的 plan chip 用 useProjection 渲染一个常驻状态 chip，已经是「只读投影 + 常驻状态」的成熟形态；插件管理器的 slot 契约提供 subject 机制，可让区块只在特定主体成立时渲染。externalClaude Code 在退出时按有无改动决定自动删或提示。
Rationale
「改动去哪了」是 worktree 类功能的头号投诉来源。把隔离态做成常驻但安静的信息，把打扰集中到唯一真正需要决策的那一刻，决定这个开关是被日常使用还是被当成噪音关掉。
Downsides
「安静」有代价：用户可能真的忘了自己在 worktree 里，直到推送时才发现分支不对。需要靠出口提示的强度来兜底，而不是靠入口教育。
Confidence 78%Complexity Low
6

默认即弃：回收挂到会话生命周期 + TTL

Description
把清理从「用户的动作」改成「会话生命周期的副作用」。默认给每个自动创建的 worktree 一个到期时间（如 24h，可续期或改为手动保留）；会话空闲且 worktree 无未提交、无未合并 commit 时到期回收；有改动则转保留并提示。开关旁显示这些副本占了多少磁盘。
Axis
3 回收与生命周期
Basis
directalpha.2 的 worktree README：「移除、清理注册信息与删除分支由用户或其他消费方负责」——即当前无人自动回收。第三方 /worktree finalize 已有 cleanup | retain_24h | retain_3d | retain_manual 这套保留等级。externalNeon branch 的 expires_at TTL；Cursor 的 Windows 磁盘事故（一周约 140GB）。
Rationale
开关把「建副本」的成本降到一次点击，就必须同时把「删副本」降到零，否则开启开关等于开启一个每周上百 GB 的泄漏。挂到会话生命周期是唯一不需要用户记住「清理」这个动作的设计。
Downsides
自动回收永远有误删风险。默认必须是「有改动就保留」，且回收动作要留可追溯的记录，否则一次误判就摧毁信任。
Confidence 76%Complexity Medium
7

fail-closed 预检：失败就什么都不发生

Description
准备序列（物化 worktree、必要的初始化）任一步失败，就拒绝开跑并显式报错——绝不回落到父仓库 cwd 静默继续。用户按下发送后如果失败，得到的是「什么都没发生」，而不是一个以为在隔离目录、实际在改主仓的会话。能前移到勾选那一刻做的校验（仓库是否可用、落点是否被占）就前移，因为那时还没有 prompt 被吞掉。
Axis
1 触发时机与状态机
Basis
directalpha.2 的 worktree README 明确列出确定会失败的类别：不获取远端对象、不初始化子模块、不装依赖、不复制未提交文件，且检出时禁用 clean/smudge/process 过滤器。reasoned静默回落是「以为在隔离、实际没隔离」，其错误代价高于任何一次显式失败；本会话今天就实际踩到过同类事故（创建失败让会话无法开始）。
Rationale
建树是这个切片里唯一会失败、且失败代价最高的步骤——用户已经把 prompt 打完了。把校验前移到零成本时机、把失败定义成硬停，能让「打了半天的 prompt 掉进虚空」这件事不发生。
Downsides
预检本身有成本（要在勾选时探一次仓库），且预检通过不等于兑现一定成功（TOCTOU）。硬失败也可能在仓库处于某些合法状态时过于严格。
Confidence 72%Complexity High

Rejection Summary

#IdeaReason Rejected
R1首次编辑前才移入（pre-step 写意图）basis 被过度解读——plan-mode 的 agent/pre-step 监听做的是 append 计划状态，与「写意图」无关；且与「cwd 创建后不可变」直接矛盾（稍后移入不可能）。
R2共享 .git 三坑在创建时一次修好被 direct 反证——alpha.2 决策笔记把子模块与依赖安装明确列为「独立操作」，并否决「创建时扩大写权限」，依据实际反对该主张。
R3乐观预建 + 幂等复位把延迟移出首字路径依据不足——引用只证明现有创建路径是「建目录 → 建 agent」，与「预建 worktree」无关；外部耗时数字无法核证。作为方向 1 的实现细节而非独立方向。
R4命名即身份 / 路径即索引 / 无注册表独立的「无注册表」主张只有外部先例支撑、未核；其可用内核（确定性命名）已并入方向 2。
R5落点预告自检（默认落点被多插件共用）「多插件共用同一落点」无出处（实测各插件落点互不相同）；自检内核并入方向 2 与方向 7。
R6创建即写 delivery 契约，接 finish / PR / 验收依据拼接——所引 auto-review 文档讲的是 composer 权限选择器，与 delivery / finish 无关；且验收流程属另一切片。
R7扇出 / best-of-N：勾选集数 = 并行度外部产品行为未核；与「一会话一树」的出生地模型冲突，属另一产品方向。
R8去掉勾选框，默认进 worktree与用户明确要求的「勾选后再自动创建」方向相反；且外部依据未核。
R9假设 git 不存在 → COW overlay 隔离层词面类比——Neon 的分支是存储层 COW，与工作目录的文件系统 overlay 不同层；且仓库大量工具假设 git 存在。
R10假设没有用户 → agent 自主决定隔离超出本切片——提案部分无直接依据，且把产品形态换成「agent 自主」，与用户勾选的交互前提冲突。
R11假设 1000 并发 → 拓扑图 + 供给池过度设计——当前环境只有 2 个已注册 workspace，规模前提不成立。
R12EDL conform：worktree 丢失可从会话重建与不可变 cwd 冲突——重建等价于新会话，「接回原会话继续」做不到。
R13worktree 是 lineage 上的分支点而非目录概念外推——引用的是 subagent 血缘与 fork 机制，外推到 worktree 身份无直接支撑。
R14场记板 / 看板卡 / 航空放行单 / 图书馆预约 / 律所保留表 / 细胞 G1-S 检查点 / 无服务器热池类比框架而非独立方向——其可用内核已被更高层方向吸收（命名 → 2；可见凭据 → 5；TTL 回收 → 3 / 6；fail-closed → 7；预热 → 1 的实现细节）。
R15永不 TTL 的时间线（每 prompt 冻结一帧）保留为方向 6 的对立参照，但未入选——在 2GB 级仓库上等于把 Cursor 的磁盘事故设成默认行为。
